# 複数の要求を同時に処理する（バッチスロット）

`"parallel"`（エンジンの `--batch N`、別名 `--slots N`）は、エンジンが最大 N 個の会話を開いたままにし、**まとめて** decode する機能です（upstream の #465、エンジンは PR #559）。
検証のウィンドウが会話ごとに 1 トークンずつ運ぶので、密な重み、共有エキスパート、ヘッド、2 つの会話が共有するエキスパートは、ウィンドウごとに全員の分を 1 回で読みます。

既定は `"auto"` で、サーバーが起動のたびにこの機械（カードの VRAM、エキスパートの大きさ、文脈の長さ）から決めます。機械によっては 1 つずつになります。

## 有効にする

モデルの設定（`xestrata-<model>.json`）の `"parallel"` は、次の 3 つです。

```json
"parallel": "auto"     // 既定: この機械に合わせて決める（起動のたびに読み直す）
"parallel": 2          // その数で固定する（setup --parallel 2 でも同じ）
"parallel": 1          // 1 つずつ（切る）
```

setup は、この機械で自動が選ぶ数を表示します（下）。指定した数は、勧める数より多くてもそのまま使い、その旨を表示します。

| オプション | 働き |
| --- | --- |
| `"parallel": N` / `--batch N` / `--slots N`（2〜8） | 最大 N 個の会話をまとめて decode します。それより多い要求は空きスロットを待ちます。スロットごとに専用のセッション（GDN の再帰状態、QSA の K/V とインデクサ、PLE の履歴）を持ちます。 |
| `"batch_groups": G` / `--batch-groups G` | 層の分割のとき、N 個のスロットを G 個の組に分け、段ごとに別の組を同時に計算します（[MULTIGPU](MULTIGPU.ja.md#まとめて-decode-するとき)）。自動では、層の分割で 2 スロット以上のとき `"auto"` になり、エンジンが割り切れる最も多い組を選びます。 |
| `--batch-mtp` / `--no-batch-mtp` | `--mtp` があれば既定で有効です（upstream 8cfb3fd7、c8c79b17。upstream では opt-in）。各スロットが窓ごとに MTP の下書きを 1 つ一緒に確かめ、合えば 2 トークン進みます。下書き層の重みは共有し、スロットごとの状態は約 50 MiB です。窓に入らない数のスロットは順に回るので、8 を超える `"parallel"` も使えます。層の分割では、スロットごとの下書き器を最後の GPU に置きます（[MULTIGPU](MULTIGPU.ja.md#まとめて-decode-するとき)）。`XESTRATA_BATCH_MTP=0` でも切れます。 |

エンジンは動かせない数を拒否しません。ログにそう書いて、動かせる数で動きます。
上限は 8 スロット（ウィンドウは 8 行）で、VRAM に収まる数まで、2 つも収まらなければスロットなし（1 つずつ）です。
「収まる」は、スロットのセッション、`--batch-mtp` のスロットごとの下書き器、使える大きさのエキスパートキャッシュがそろって入ることです。入らなければ、エンジンは後ろのスロットから返し、起動時のログに動かせた数を書きます。
サーバーはエンジンが報告する数（`INFO batch_slots=N`）を読み、`GET /v1/status` の `concurrency.serving` に出します。

`--batch-mtp` は、温度 0、4 スロットで 200 トークンずつの 4 つの要求で、どのスロットも 1 つずつ生成したときと同じトークンを出しました（`tools/batch_test.py`、`--pcie-frac 0 --adapt-every 1000000`）。
合計の速さは、B70 で 87.4 / 86.8 → 90.6 / 90.6 トークン/秒、RTX 4070 で 45.2 / 44.0 → 44.6 / 43.8 トークン/秒（ばらつきの範囲）でした。

### スロットの費用と、自動の決め方

スロットのセッションは、エキスパートキャッシュに使えたはずの VRAM を使います。
8 ビットの KV で 32K のコンテキストなら 1 スロット約 0.6 GB で、コンテキストが長いほど増えます。
KV を流す場合（`--kv-resident N`）は、各 QSA 層の N セルだけが VRAM に残り、各スロットの KV キャッシュ全体はピン留めした RAM を使います。
エキスパートの多くを CPU で計算するカードでは、会話ごとに違うエキスパートに振り分けられるため、バッチでも 1 つずつとほぼ同じ数のエキスパートを読みます。
得られるのは**待ち時間**の短縮で、1 つだけの要求はキャッシュが減った分だけ遅くなります（upstream の測定で 12 GB のカードで 11〜24 %）。

そこでサーバーは、**エキスパートの多くが VRAM に収まる所でだけ**スロットを使います（setup も同じ数を表示します）。
エキスパートキャッシュ（カードの VRAM から約 5 GB を引いた分）が、スロットを置いてもモデルのエキスパートの半分以上を持て、スロットが使うのはその 5 分の 1 まで、最大 4 スロットです。
32K のコンテキストの int8 の KV では、64 GB のカードで IQ3_XXS（エキスパート 50.3 GB）が 4 スロット、24 GB のカードでは同じモデルが 1 つずつ（Q2_0 の 34.0 GB なら 3 スロット）です。1 つずつのときは「parallel N reduces waiting for several users but costs about 10-25% speed per request on this card」と表示します。
モデルのファイルの大きさは setup が設定に書きます（`"model_gb"`・`"experts_gb"`）。手で書いた設定で分からないときは、1 つずつです。

起動のログは、選んだ数とその理由を 1 行ずつ出します。
自動で 2 つ以上になったときは、**最初の要求**でも確かめます。1 本だけで decode している間の速さと、2 本が並んで decode している間の合計を 1 秒ごとに採り、中央値で比べます。合計が 1 本の 1.05 倍に届かなければ、走っている要求が終わったところで 1 つずつに戻します（エンジンはスロットを VRAM に持ったままですが、サーバーは 1 本ずつしか入れません）。結果はファイルに残さず、起動のたびに測り直します。

## サーバーがスロットを使う方法

- **要求が 1 つだけ**のときは、いつもの単独の経路（MTP の推測つきの検証ウィンドウ）で動きます。1 本の流れとしてはこれが最速です。
- **2 つ目の要求が来る**と、1 つ目を止め（`STOP`）、プロンプトとそれまでに生成した分を持ってバッチスロットで続けます。
  エンジンのプロンプトキャッシュがちょうどその内容を持っているので、読み直しはありません。新しい要求はその横に入ります。
  スロットの要求は **MTP の推測なし**で decode します（ウィンドウごとに 1 トークン）。
- **スロットに 1 つだけ残った要求**（ほかが終わり、待つ要求もない）は、単独の経路に戻ります。
  スロットを止め、エンジンがセッションを戻して、また MTP の推測つきで decode します（1 要求につき 2 回まで。`--prompt-cache 0` ならスロットに残ります。`XESTRATA_PARALLEL_SOLO=0` でオフ）。
- **スロットより多い要求**は空きを待ちます（`/metrics` の `live.slots` に、スロットごとの状態（空き、読み込み中、decode 中）、トークン数、tok/s が出ます）。
- **受け入れ**のたびに、要求のプロンプトをいつもの prefill の経路（プロンプトキャッシュと会話のチェックポイントを含む）で読み、そこで最初のトークンを出してから、状態をスロットにコピーします。
  受け入れは 1 つずつで、**prefill のチャンクの合間にスロットが decode します**。
  チャンクを 1 つ読むたびに、その所要時間の半分だけ decode します（`XESTRATA_BATCH_DECODE_SHARE`、既定 0.5）。長いプロンプトはほかの会話を止めずに遅くするだけです。
  チャンクの区切りは中断なしで読むときと同じなので、prefill の計算は変わりません。
- **長いプロンプトは短いものに譲ります**。半分より短いプロンプトの要求が待っていると、サーバーは `BYIELD` を送ります。
  長い読み込みは次のチャンクの区切りで止まり、読んだ分をスロットにコピーし、短い要求を受け入れてから、スロットから同じチャンクで続けます（1 要求につき 2 回まで）。
- **各スロットは会話のキャッシュです**。終わったスロットは持っている内容（プロンプト、答え、プロンプトの最後のターンの区切りのチェックポイント）を残します。
  その会話の次のターンは同じスロットに送られ、エンジンは履歴を読み直さずに状態をコピーして戻します。
  答えの思考部分を履歴から外すクライアントでも、チェックポイントが新しいターンの手前まで一致します。
  最後の質問を差し替えた分岐も、その前の 2 ターン以上が一致していれば同じスロットに送られ、ほかの会話のスロットを上書きしません。
  新しい会話は空きスロットを、なければいちばん前に使ったスロットを使います。
  ただし要求に `prompt_cache_key`（OpenAI のフィールド。Mainplane などはセッションごとに送ります）があれば、同じキーの要求が前に使ったスロットを先に使い直します。
- 接続を切ったクライアントはそのスロットを止めます（`BSTOP`）。ほかのスロットは続きます。

### 単独の経路からスロットに移る長いプロンプト

単独の経路からスロットに移るとき読み直さないのは、エンジンのプロンプトキャッシュがいまのセッションを使い回すからです。
`--prompt-cache 0` では、移った要求はプロンプト全体を読み直します。
RAM を減らすためにキャッシュを絞るときも、移るときの使い回しだけを残すなら、設定の `args` を次のようにします（ほかの引数はそのまま）。

```text
"args": [ ..., "--prompt-cache", "1", "--prompt-cache-every", "0",
          "--prompt-cache-root", "0", "--conversation-cache-mib", "0" ]
```

`--prompt-cache 1` はチェックポイントを 1 つにし、`--prompt-cache-every 0` は 16K トークンごとのチェックポイントを、`--prompt-cache-root 0` はシステムプロンプトのチェックポイントを取らなくします。
`--conversation-cache-mib 0` は終わった会話を RAM に置かなくするだけで、チェックポイントも、スロットが持つセッションも残します。
会話を置いておく設定をすでに使っているなら、その大きさはそのままにします（移るときの使い回しとは別の設定です）。
これで、新しい長いプロンプトを同時に読むようにはなりません。受け入れは 1 つずつです。

## バッチのウィンドウでも VRAM の層を適応させる

バッチのウィンドウも、どのエキスパートに振り分けたかを数えます（upstream e989c671）。
`--adapt-every` ウィンドウごと（既定 4）に、単独の経路と同じ規則で、VRAM にないよく使われるエキスパートを、キャッシュのあまり使われないエキスパートと入れ替えます。
`--adapt-swaps` と `--adapt-decay` も効き、層の分割では各 GPU のキャッシュが適応します。
入れ替えはウィンドウの commit・出力・下書きの横で進み、次のウィンドウの前に着地します。
decode 中のスロットの横で長いプロンプトを読んでいる間（プロンプトがキャッシュのスロットを借りていることがあります）は止まります。
`--adapt-async`（RAM 常駐のモードで既定）では、1 回分を待たずに、バッチのウィンドウごとに 1 歩ずつ進めます（upstream 495dc436）。新しい要求は、進行中の回を終えてから始まります。
`--batch-groups` で組をパイプラインにしたときは、既定では適応しません。振り分けは数えますが、組が流れている間は回を始めないので、スロットが単独の経路に戻ったときにしか層が動きません。
`XESTRATA_PIPE_ADAPT_EVERY=N`（明示的に有効にする機能。なし・0 なら今までどおり）を付けると、パイプラインでも適応します（upstream a3bb38ec4）。
組のウィンドウ N 回ごとに新しい組を始めず、流れている組が終わるのを待ってから、直列のバッチのウィンドウと同じ 1 回を回して続けます。どのカードにもホストを待つウィンドウがない間に入れ替えるので、入れ替え中のキャッシュのスロットを読むウィンドウはなく、入れたエキスパートは次の組の前に着地します。
decode 中のスロットの横でプロンプトを読む間と `--adapt-async 1` では何もしません。起動時のログにその旨が出て、`xestrata batch (pipelined ...)` の行に回数、入れ替えたエキスパートの数、かかった時間が足されます。
upstream の測定（2x RTX 5090、層の分割、`--batch 6 --batch-groups 2`、`--adapt-every 16`、起動直後の 6 本の流れの 8 回）では、なしの平均 309 行/s に対し、128 で 410 行/s、32 で 402 行/s でした（32 はパイプラインを 4 倍空けるぶん少し低い）。
`xestrata batch:` のログの行に、適応の回数、入れ替えたエキスパートの数、ウィンドウあたりの待ち（`adapt wait`）が出ます。
入れ替えでエキスパートが GPU と CPU のあいだを移り、丸めが変わるので、貪欲な出力も実行ごとに変わることがあります。層を固定するには `--adapt-every 1000000` を渡します（下の「一致」）。

## 流れ作業の組でも MTP の下書きを確かめる（`XESTRATA_PIPED_MTP`、明示的に有効にする機能）

組に分けたウィンドウ（`--batch-groups` が 2 以上）は MTP の下書きを確かめず、1 組の `--batch-mtp` は一度に 1 枚の GPU しか動きません。
`--batch-mtp` と一緒に `XESTRATA_PIPED_MTP=N` を付けると、組の流れ作業のまま、各スロットが下書きを確かめます（upstream 17878ac57）。
付けなければ何も変わりません。

組のウィンドウは、組の各スロットについて、そのトークンと最大 N 個の MTP の下書き（`--spec` - 1 まで。1 つ目は必ず、2 つ目からは下書き層が 1 つ前を `--spec-min-p` 以上の確かさで出したとき）を運びます。
最後の GPU が各スロットの下書きを別々に判定します。
何行を残すかはそこで初めて決まり、そのとき前の GPU はもうほかの組のウィンドウを計算しているので、commit が読み直す行は各ウィンドウのすぐ後ろで組ごとの保存先にコピーしておき、判定の後に各 GPU で残す行の commit を積みます。
前の GPU の commit は、その GPU にホストを待つウィンドウがない間（次のウィンドウを出す前か、空いているとき）にだけ積みます。
スロットの下書き器は自分の行に追いついてから、次の下書きを非同期の連鎖として作ります。連鎖が終わっていない組は、ほかの組に先を譲ります。
受け入れ、置いた会話、単独の経路への戻りなど、スロットの状態を読む処理の前には、流れている組と積んだ commit をすべて終わらせます。

層の分割で 2 組以上、組のウィンドウ（組のスロット数 × (1 + N)）が 8 行以内のときに動きます。
動かせないときはそう言って外し、組に分けたままなら `--batch-mtp` も切ります。
各 GPU に保存先（upstream の測定で 4 スロットのとき `=1` で 25.5 MiB、`=2` で 38.2 MiB）が要り、エキスパートキャッシュから取ります。

upstream の測定では `=1` が最もよい設定です。
2x RTX A6000（全エキスパートが VRAM、`--batch 4` で 2 スロットの 2 組、合計 tok/s）では、2 本の流れで下書きなしの 125.7 に対し `=1` 146.3（+16%）、`=2` 145.1、4 本で 171.4 に対し `=1` 188.8（+10%）、`=2` 179.5、`=3` 165.6 でした。
2x RTX A4000（Q2_0、エキスパートが VRAM に入りきらない）では、2 本で `=1` が +18〜20%、4 本で `=1` が +6〜8%、`=2` は下書きなしより遅くなりました。
1 本の流れは単独の経路で動くので変わりません。
貪欲な出力は、どのスロットも単独で動かしたときと同じでした（upstream、A6000）。エキスパートが VRAM に入りきらない構成では、下書き器の VRAM の分だけキャッシュに入るエキスパートが変わり、出力が変わることがあります。

## 一致

バッチの行の計算は 1 トークンのウィンドウと同じなので、貪欲 decode なら**バッチのどの会話も、単独で動かしたときとまったく同じトークンを出します**。
B70 で、3 つの会話を同時に、decode 中の 2 つの横で読む長いプロンプトを、スロットから続けた次のターンを、それぞれ単独と比べて確かめました。
比較を厳密にするには次の設定を使います。

- `--pcie-frac 0`: 外れたエキスパートの PCIe の割り当てはウィンドウの外れから毎回決まるので、同じエキスパートがあるウィンドウでは GPU、別のウィンドウでは CPU で計算され、丸めが変わります。
- `--adapt-every 1000000`（VRAM の層を固定）と、decode 中のスロットの横でプロンプトを読むときの `--no-prefill-borrow`。
  プロンプトが借りたキャッシュのスロットのエキスパートは、その間スロットのウィンドウでは CPU で計算されます。

既定の設定では、出力は意味の通るまま、いくらかのトークンのあとで離れていきます。ウィンドウの違う 2 回の単独の実行と同じです。

サンプリングする要求（temperature、top_p、top_k、min_p、seed）は、行ごとに単独のウィンドウと同じカウンター式の乱数（Philox(seed, 位置)）で引きます。

## いまの限界

- バッチのウィンドウは MTP の推測を運びません。スロットの会話はウィンドウごとに 1 トークンです（単独の経路は推測を保つので、1 つだけの要求はスロットに入れず、1 つだけ残れば戻します）。
- 繰り返し・頻度・存在のペナルティは、バッチのウィンドウでは効きません。
- 1 チャンクより短いプロンプトは一度に読みます（その間スロットは待ちます）。読み込みが譲るのはチャンクの区切りだけで、画像のときは譲りません。
- 受け入れは 1 つずつです。2 つの新しい長いプロンプトは順に読みます。
- スロットのセッションは VRAM を使い（上）、KV を流す場合はピン留めした RAM も使います。

## ほかのモデル（plain のエンジン）

Ornith-1.5、llm-jp-4.1、Qwen3.6-35B-A3B、Qwen3.5-9B も、同じ `"parallel"`（`"auto"` が既定）でスロットを使います（GLM-5.3-Flash と `--vision` ではまだ使えません。自動の決め方は Qwen3.8-Flash-Next と同じで、モデルの種類ではなく、重みとエキスパートの大きさとカードの VRAM から決めます）。
サーバーの使い方（単独の経路からスロットへ移ること、スロットごとの会話のキャッシュ、`prompt_cache_key`）は Qwen3.8-Flash-Next と同じです。

- スロットは最大で `--max-t`（既定 8）個です。各スロットの状態は、エキスパートの VRAM の層より先に、その時点の空き VRAM の半分までで取り、取れた数を起動のログが言います。
- 1 スロットの大きさは文脈の長さに比例します（Qwen3.6-35B-A3B で 16K の文脈なら 414 MiB、128K なら 2,878 MiB。Qwen3.5-9B は 16K で 562 MiB）。
- MTP の層のあるモデルでは、Qwen3.8-Flash-Next と同じく、各スロットが窓ごとに MTP の下書きを 1 つ一緒に確かめ、合えば 2 トークン進みます（`--batch-mtp`、既定で有効。`--no-batch-mtp` か `XESTRATA_BATCH_MTP=0` で切れます）。窓に入るのは `--max-t` 行までなので、それを超える分のスロットはその窓では下書きなしで進みます。スロットごとに、最初の行の後の再帰の状態の写しを持ちます（Qwen3.6-35B-A3B で約 60 MiB）。
- プロンプトを読む間、スロットは待ちます（チャンクの間に decode しません）。`BYIELD` は受け取っても何もしません。
- スロットのウィンドウは、スロットの組み合わせごとに 1 度グラフに記録します。
- 層の分割では、Qwen3.8-Flash-Next と同じく、スロットを組に分けて段をまたいで流します（`--batch-groups G`・`auto`。層の分割では既定で `auto`）。各段が別の組を同時に計算し、組の窓は下書きを運ばないので、`--batch-mtp` はそのとき切れます（`--batch-groups 1` か `XESTRATA_BATCH_MTP_SERIAL=1` で 1 組のまま下書きを使います）。組が段にいる間は、適応の段は入れ替えません。B70 と RTX 4070 の分割（層 20 で分ける）で Qwen3.6-35B-A3B を 4 スロット回すと、1 組・下書きなしの 66.1、1 組・下書きありの 69.2 に対し、2 組で 89.3 トークン/秒でした。

B70 で `tools/batch_test.py`（貪欲 decode）を 4 スロットで回すと、次のとおりでした。

- Qwen3.5-9B Q4_K_M: 64 トークン 4 本が単独と同じトークンで、合計 111 トークン/秒でした（1 本ずつは約 52）。
- Qwen3.6-35B-A3B UD-Q4_K_XL: `--no-pcie-split --adapt-every 0` では 4 本とも単独と同じトークンでした。VRAM に 3,000 枠だけ置いて CPU のエキスパートが混ざる設定でも、`--pcie-frac 0 --adapt-every 0` なら 4 本とも同じでした。適応の段（prompt の後の入れ替えも）が動くと、単独と枠でエキスパートを計算する場所（GPU か CPU）が変わり、丸めの違いで引き分けに近いトークンが入れ替わることがあります。PCIe で読む割合を 0 より大きくしても、枠の窓では 1 層の外れたエキスパートが写しの枠を超えた分を CPU が計算するので、同じことが起きます。既定の設定では、128 トークン 4 本が合計 186 トークン/秒でした（1 本ずつ MTP の推測つきで約 140）。

## 測定

B70（32 GB）、i7-14700、Qwen3.8-Flash-Next IQ2_XS、エンジンへ直接、3 つの会話を貪欲 decode で:
3 行のウィンドウが平均 32.8 ms で 72.1 行/s、1 行のウィンドウは 21.6 ms で 46.1 行/s でした。
3 つの会話を合わせた速さは 1 行ずつの 1.56 倍です。

## テスト

`serve/test_parallel.py` は、台本どおりに答える偽のエンジンでサーバーの側を確かめます（GPU は要りません）。
`tools/test_setup_parallel.py` は setup が勧める数を確かめます。
次の 4 つは、ビルドしたエンジンか動いているサーバーを使い、失敗すると 0 以外で終わります。

| スクリプト | 確かめること |
| --- | --- |
| `tools/batch_test.py` | 同じプロンプトを単独（`GEN`）とバッチスロット（`BGEN`）で読み、どのスロットの貪欲なトークンも単独と同じこと。合わせた速さも表示します。`--keys "temperature=0.7"` でサンプリングする行を試します。 |
| `tools/batch_interleave_test.py` | 2 つのスロットが decode する横で読む長いプロンプト、譲って（`BYIELD`）から続けるプロンプト、スロットから続ける次のターンが、それぞれ単独と同じこと。 |
| `tools/parking_test.py` | 会話の続きが、状態が生きていたときと、置いた会話から戻したときで同じトークンになること。 |
| `tools/early_close_test.py` | 流している答えをクライアントが途中で読むのをやめても（単独のときと、もう 1 つの要求が動いているとき）、そのトークンが次の要求に残らないこと（サーバー）。 |

厳密に比べるには `--pcie-frac 0 --adapt-every 1000000` を渡します。

```sh
    --extra "--pcie-frac 0 --adapt-every 1000000 --no-prefill-borrow"
python3 tools/parking_test.py --exe build/contrib-llvm/xestrata-engine --config xestrata-<model>.json \
    --extra "--conversation-cache-mib 8192 --conversation-cache-slots 4 --pcie-frac 0 --adapt-every 1000000"
XESTRATA_KEY=<key> python3 tools/early_close_test.py http://127.0.0.1:8095
```

## エンジンのプロトコル（`--serve`）

`GEN` / `GENI` に加えて:

| 行 | 向き | 意味 |
| --- | --- | --- |
| `BGEN <slot> <max_new> [keys] <ids>` | 入 | プロンプトを（`GEN 1` と同じく）読み、`<slot>` で続けます |
| `BGENI <slot> <max_new> [keys] <file> <ids>` | 入 | 同じく、画像つき |
| `BADM <slot> <1/0>` | 出 | 受け入れの `DONE` のあと: 1 = スロットで続ける、0 = 終わった |
| `BT <slot> <id>` | 出 | そのスロットのトークン |
| `BDONE <slot> <generated> <stop/length/cancel> <ms>` | 出 | スロットが空いた（会話は残す） |
| `BSTOP <slot>` | 入 | 次のウィンドウでそのスロットを終える |
| `BYIELD <slot>` | 入 | 読み込み中のプロンプトが次のチャンクの区切りで譲り、読んだ分は `<slot>`（受け入れのスロット、単独の要求なら空きスロット）で待ちます |
| `YIELDED <slot> <tokens>` | 出 | 譲った読み込みの `DONE cancel` の前: 要求はあとで送り直され、そこから続きます |
| `INFO ... batch_slots=N slot_cache=1` | 出 | エンジンが動かすスロットの数（`--batch` のときだけ）と、スロットが会話を持つこと |
