# 複数の要求を同時に処理する（バッチスロット）

既定では、XeStrata は**要求を 1 つずつ**処理し、ほかの要求はサーバーのキューで待ちます。
`"parallel": N`（エンジンの `--batch N`、別名 `--slots N`）を付けると、エンジンは最大 N 個の会話を開いたままにし、**まとめて**デコードします。
検証のウィンドウが会話ごとに 1 トークンずつ運ぶので、密な重み、共有エキスパート、ヘッド、2 つの会話が共有するエキスパートは、ウィンドウごとに全員の分を 1 回で読みます。

明示的に有効にする機能で、オプションがなければ何も変わりません（upstream の #465、エンジンは PR #559）。

## 有効にする

モデルの設定（`strata-<model>.json`）に `"parallel": 2` を足して再起動するか、setup を `--parallel 2` で実行します。
setup は速さを落とさない所でだけ勧めます（下）。指定した数は、勧める数より多くてもそのまま使い、その旨を表示します。

```json
"parallel": 2
```

| オプション | 働き |
| --- | --- |
| `"parallel": N` / `--batch N` / `--slots N`（2〜8） | 最大 N 個の会話をまとめてデコードします。それより多い要求は空きスロットを待ちます。スロットごとに専用のセッション（GDN の再帰状態、QSA の K/V とインデクサ、PLE の履歴）を持ちます。 |
| `--batch-mtp` / `--no-batch-mtp` | `--mtp` があれば既定で有効です（upstream 8cfb3fd7、c8c79b17。upstream では opt-in）。各スロットが窓ごとに MTP の下書きを 1 つ一緒に確かめ、合えば 2 トークン進みます。下書き層の重みは共有し、スロットごとの状態は約 50 MiB です。窓に入らない数のスロットは順に回るので、8 を超える `"parallel"` も使えます。1 つの GPU だけで、層の分割では無効です。`STRATA_BATCH_MTP=0` でも切れます。 |

エンジンは動かせない数を拒否しません。ログにそう書いて、動かせる数で動きます。
上限は 8 スロット（ウィンドウは 8 行）で、VRAM に収まる数まで、2 つも収まらなければスロットなし（1 つずつ）です。
サーバーはエンジンが報告する数（`INFO batch_slots=N`）を読み、`GET /v1/status` の `concurrency.serving` に出します。

`--batch-mtp` は、温度 0、4 スロットで 200 トークンずつの 4 つの要求で、どのスロットも 1 つずつ生成したときと同じトークンを出しました（`tools/batch_test.py`、`--pcie-frac 0 --adapt-every 1000000`）。
合計の速さは、B70 で 87.4 / 86.8 → 90.6 / 90.6 トークン/秒、RTX 4070 で 45.2 / 44.0 → 44.6 / 43.8 トークン/秒（ばらつきの範囲）でした。

### スロットの費用と、setup が勧める数

スロットのセッションは、エキスパートキャッシュに使えたはずの VRAM を使います。
8 ビットの KV で 32K のコンテキストなら 1 スロット約 0.6 GB で、コンテキストが長いほど増えます。
KV を流す場合（`--kv-resident N`）は、各 QSA 層の N セルだけが VRAM に残り、各スロットの KV キャッシュ全体はピン留めした RAM を使います。
エキスパートの多くを CPU で計算するカードでは、会話ごとに違うエキスパートに振り分けられるため、バッチでも 1 つずつとほぼ同じ数のエキスパートを読みます。
得られるのは**待ち時間**の短縮で、1 つだけの要求はキャッシュが減った分だけ遅くなります（upstream の測定で 12 GB のカードで 11〜24 %）。

そこで setup は、**エキスパートの多くが VRAM に収まる所でだけ** `"parallel"` を勧めます。
エキスパートキャッシュ（カードの VRAM から約 5 GB を引いた分）が、スロットを置いてもモデルのエキスパートの半分以上を持て、スロットが使うのはその 5 分の 1 まで、最大 4 スロットです。
32K のコンテキストでは 24 GB 以上のカードで 4 スロットになり、それより小さいカードでは 1 つずつのまま、setup は「parallel N reduces waiting for several users but costs about 10-25% speed per request on this card」と表示します。
`--parallel N` を指定すれば、どちらの場合もその数を使います。

## サーバーがスロットを使う方法

- **要求が 1 つだけ**のときは、いつもの単独の経路（MTP の推測つきの検証ウィンドウ）で動きます。1 本の流れとしてはこれが最速です。
- **2 つ目の要求が来る**と、1 つ目を止め（`STOP`）、プロンプトとそれまでに生成した分を持ってバッチスロットで続けます。
  エンジンのプロンプトキャッシュがちょうどその内容を持っているので、読み直しはありません。新しい要求はその横に入ります。
  スロットの要求は **MTP の推測なし**でデコードします（ウィンドウごとに 1 トークン）。
- **スロットに 1 つだけ残った要求**（ほかが終わり、待つ要求もない）は、単独の経路に戻ります。
  スロットを止め、エンジンがセッションを戻して、また MTP の推測つきでデコードします（1 要求につき 2 回まで。`--prompt-cache 0` ならスロットに残ります。`STRATA_PARALLEL_SOLO=0` でオフ）。
- **スロットより多い要求**は空きを待ちます（`/metrics` の `live.slots` に、スロットごとの状態（空き、読み込み中、デコード中）、トークン数、tok/s が出ます）。
- **受け入れ**のたびに、要求のプロンプトをいつものプロンプトの経路（プロンプトキャッシュと会話のチェックポイントを含む）で読み、そこで最初のトークンを出してから、状態をスロットにコピーします。
  受け入れは 1 つずつで、**プロンプトのチャンクの合間にスロットがデコードします**。
  チャンクを 1 つ読むたびに、その所要時間の半分だけデコードします（`STRATA_BATCH_DECODE_SHARE`、既定 0.5）。長いプロンプトはほかの会話を止めずに遅くするだけです。
  チャンクの区切りは中断なしで読むときと同じなので、プロンプトの計算は変わりません。
- **長いプロンプトは短いものに譲ります**。半分より短いプロンプトの要求が待っていると、サーバーは `BYIELD` を送ります。
  長い読み込みは次のチャンクの区切りで止まり、読んだ分をスロットにコピーし、短い要求を受け入れてから、スロットから同じチャンクで続けます（1 要求につき 2 回まで）。
- **各スロットは会話のキャッシュです**。終わったスロットは持っている内容（プロンプト、答え、プロンプトの最後のターンの区切りのチェックポイント）を残します。
  その会話の次のターンは同じスロットに送られ、エンジンは履歴を読み直さずに状態をコピーして戻します。
  答えの思考部分を履歴から外すクライアントでも、チェックポイントが新しいターンの手前まで一致します。
  新しい会話は空きスロットを、なければいちばん前に使ったスロットを使います。
- 接続を切ったクライアントはそのスロットを止めます（`BSTOP`）。ほかのスロットは続きます。

## 一致

バッチの行の計算は 1 トークンのウィンドウと同じなので、貪欲デコードなら**バッチのどの会話も、単独で動かしたときとまったく同じトークンを出します**。
B70 で、3 つの会話を同時に、デコード中の 2 つの横で読む長いプロンプトを、スロットから続けた次のターンを、それぞれ単独と比べて確かめました。
比較を厳密にするには次の設定を使います。

- `STRATA_IQ_MT_MIN=1`: CPU のエキスパートのカーネルを、どのグループでも複数トークン用にします。
  既定では、エキスパートの行が 1 行だけのときとグループのときで丸めが違うので、ウィンドウのいくつの行がエキスパートを共有するかで出力が変わります（バッチと単独では違います）。
- `--pcie-frac 0`: 外れたエキスパートの PCIe の割り当てはウィンドウの外れから毎回決まるので、同じエキスパートがあるウィンドウでは GPU、別のウィンドウでは CPU で計算され、丸めが変わります。
- `--adapt-every 1000000`（VRAM の層を固定）と、デコード中のスロットの横でプロンプトを読むときの `--no-prefill-borrow`。
  プロンプトが借りたキャッシュのスロットのエキスパートは、その間スロットのウィンドウでは CPU で計算されます。

既定の設定では、出力は意味の通るまま、いくらかのトークンのあとで離れていきます。ウィンドウの違う 2 回の単独の実行と同じです。

サンプリングする要求（temperature、top_p、top_k、min_p、seed）は、行ごとに単独のウィンドウと同じカウンター式の乱数（Philox(seed, 位置)）で引きます。

## いまの限界

- バッチのウィンドウは MTP の推測を運びません。スロットの会話はウィンドウごとに 1 トークンです（単独の経路は推測を保つので、1 つだけの要求はスロットに入れず、1 つだけ残れば戻します）。
- 繰り返し・頻度・存在のペナルティは、バッチのウィンドウでは効きません。
- 1 チャンクより短いプロンプトは一度に読みます（その間スロットは待ちます）。読み込みが譲るのはチャンクの区切りだけで、画像のときは譲りません。
- 受け入れは 1 つずつです。2 つの新しい長いプロンプトは順に読みます。
- スロットのセッションは VRAM を使い（上）、KV を流す場合はピン留めした RAM も使います。

## 測定

B70（32 GB）、i7-14700、Qwen3.8-Flash-Next IQ2_XS、エンジンへ直接、3 つの会話を貪欲デコードで:
3 行のウィンドウが平均 32.8 ms で 72.1 行/s、1 行のウィンドウは 21.6 ms で 46.1 行/s でした。
3 つの会話を合わせた速さは 1 行ずつの 1.56 倍です。

## テスト

`serve/test_parallel.py` は、台本どおりに答える偽のエンジンでサーバーの側を確かめます（GPU は要りません）。
`tools/test_setup_parallel.py` は setup が勧める数を確かめます。
次の 4 つは、ビルドしたエンジンか動いているサーバーを使い、失敗すると 0 以外で終わります。

| スクリプト | 確かめること |
| --- | --- |
| `tools/batch_test.py` | 同じプロンプトを単独（`GEN`）とバッチスロット（`BGEN`）で読み、どのスロットの貪欲なトークンも単独と同じこと。合わせた速さも表示します。`--keys "temperature=0.7"` でサンプリングする行を試します。 |
| `tools/batch_interleave_test.py` | 2 つのスロットがデコードする横で読む長いプロンプト、譲って（`BYIELD`）から続けるプロンプト、スロットから続ける次のターンが、それぞれ単独と同じこと。 |
| `tools/parking_test.py` | 会話の続きが、状態が生きていたときと、置いた会話から戻したときで同じトークンになること。 |
| `tools/early_close_test.py` | 流している答えをクライアントが途中で読むのをやめても（単独のときと、もう 1 つの要求が動いているとき）、そのトークンが次の要求に残らないこと（サーバー）。 |

厳密に比べるには `--pcie-frac 0 --adapt-every 1000000` を渡します（スクリプトが `STRATA_IQ_MT_MIN=1` を設定します）。

```sh
python3 tools/batch_test.py --exe build/xe/strata --config xestrata-<model>.json --batch 3 --n 3 \
    --extra "--pcie-frac 0 --adapt-every 1000000"
python3 tools/batch_interleave_test.py --exe build/xe/strata --config xestrata-<model>.json \
    --extra "--pcie-frac 0 --adapt-every 1000000 --no-prefill-borrow"
python3 tools/parking_test.py --exe build/xe/strata --config xestrata-<model>.json \
    --extra "--conversation-cache-mib 8192 --conversation-cache-slots 4 --pcie-frac 0 --adapt-every 1000000"
STRATA_KEY=<key> python3 tools/early_close_test.py http://127.0.0.1:8095
```

2026-10-06 に B70（IQ2_XS、contrib のビルド）で 4 つとも通りました。

## エンジンのプロトコル（`--serve`）

`GEN` / `GENI` に加えて:

| 行 | 向き | 意味 |
| --- | --- | --- |
| `BGEN <slot> <max_new> [keys] <ids>` | 入 | プロンプトを（`GEN 1` と同じく）読み、`<slot>` で続けます |
| `BGENI <slot> <max_new> [keys] <file> <ids>` | 入 | 同じく、画像つき |
| `BADM <slot> <1/0>` | 出 | 受け入れの `DONE` のあと: 1 = スロットで続ける、0 = 終わった |
| `BT <slot> <id>` | 出 | そのスロットのトークン |
| `BDONE <slot> <generated> <stop/length/cancel> <ms>` | 出 | スロットが空いた（会話は残す） |
| `BSTOP <slot>` | 入 | 次のウィンドウでそのスロットを終える |
| `BYIELD <slot>` | 入 | 読み込み中のプロンプトが次のチャンクの区切りで譲り、読んだ分は `<slot>`（受け入れのスロット、単独の要求なら空きスロット）で待ちます |
| `YIELDED <slot> <tokens>` | 出 | 譲った読み込みの `DONE cancel` の前: 要求はあとで送り直され、そこから続きます |
| `INFO ... batch_slots=N slot_cache=1` | 出 | エンジンが動かすスロットの数（`--batch` のときだけ）と、スロットが会話を持つこと |
